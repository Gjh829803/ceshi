## 2. 统一判定方式

验收分别记录 `technicalDelivery`、`openingAlignment`、`subjectIntegrity`、`visibleTopology`、`routeAndSupport`、`controlsAndLifecycle`、`exploration` 和 `declaredControlCapabilities`。每项用 `passed / failed / not-verified`，附实际证据；不以一个总分抵消不可达高台、主体缺失或附件脱落。可试玩但有缺陷的产物应保留并明确标注问题。

技术交付的 MCP/归档/哈希通过，只说明这份产物和证据可以核验；不得据此判参考还原、路线语义或游戏质量通过。Creator 自己填写的 targets、reached、碰撞数量、时长或“passed”不是独立验收结论。

### 首帧与完整三维

- 在操作候选之前，使用原图标出主体轮廓、地平线或山谷层次、主要地标、通路入口、近景遮挡的对应点。比较同画幅、同宽高比的真实重置首帧；记录主体/地标二维框与相对画幅位置，不用生成结果选择“更容易匹配”的裁切或另一个出生点。
- 必须保留相机方向与俯仰感、主体占画幅比例、地标左右关系、前中后景尺度、透视消失方向和主要遮挡。可记录归一化像素偏差辅助描述；本计划不事后设数值阈值来包装通过。
- 白模可简化毛发、植被叶片、石材纹理和雕花；主要轮廓、实体层次、开口、地理关系和稳定可辨认的颜色身份不能一起消失。人物头身四肢及显著背包、披风、草帽等轮廓属于对照内容，面部写实度不作硬门槛。
- 首帧必须来自可玩的同一场景及真实相机；主体、主路线和承诺可达的地标不能由整张参考图贴片、只对初始相机成立的替身或独立“展示场景”冒充。通过侧移、回头、接近及完整目标三视图检查真实厚度与一致身份。远景天空、云雾和未承诺可达的背景轮廓可以简化表示，不要求所有远景都成为可走实体。
- 三视图应含完整主体及主要完整目标组。前/右/后按各目标的语义朝向判定；不要求每个目标使用相同世界轴，也不要求附件必须拆成独立 Mesh。

### 连续输入、生命周期和高度支撑

每个 profile 都执行下面的真实键盘/鼠标操作。独立验收可根据实际场景选择方向和安全起点；不得改场景或用坐标传送完成路线。保存按键按下/松开/重复、实际用时、相机画面和位置轨迹；有 SDK tick/接触/clip 读数时同时保存，没有时记录缺失，不能填造。

| 操作 | 需要观察的行为 |
| --- | --- |
| W/A/S/D 与四个方向键 | 在同一可走区域逐一按住、松开；方向一致且实际位移合理。箭头不能仅滚动网页。对角组合、转向、松开一个仍按住另一个时不粘键。 |
| Shift 连续跑步 | 在同一路段先走，再保持方向键按住并按下 Shift，持续跑过转向/轻微地形，松开 Shift 后仍能走；不能因重复 keydown 周期性停跑。用中间稳定区间比较移动和动画，排除起停与已确认碰撞。 |
| Space 跑跳与重复按键 | 平地和实际路线边缘各测试一次；按住/系统重复不能无约束连跳，松开后再次按下能再跳。起跳、落地及脚底高度一致，不能穿地或靠隐藏重置复原。 |
| 停步、坡道、台阶、桥和高台 | 在上下行与转弯中释放输入，角色应停在实际支撑面；从不同方向重走连接处，检查接缝、栏杆、头部净空和边缘。只看 XZ 接近目标不算到达高层。 |
| Pause / resume 与失焦 | 移动或跑步中暂停/失焦，按键释放后恢复；暂停时状态稳定，恢复后无“补跑”、残留按键、二倍时钟或重复监听器。若存在明确的游戏结束，应单独记录，不将停机时间计入探索。 |
| Reset | 移动、转向、跳跃和一次交互后重置，核对出生位置、首帧相机、完整主体、初始动作姿态、附件、对象可见性和已声明的玩法状态。再跑一遍关键动作，不能恢复成 bind pose 或保留旧速度。 |
| 镜头与遮挡 | 转动镜头、进入地标近旁并回到主路线，检查相机是否穿入大块实体、永久遮住主体、突然跳向错误主体，或尾部占满画面后无法恢复。 |

高度验收以原图要求的空间关系和候选中实际可见的支撑面为锚。审阅者独立识别桥面、平台地板、田埂等，再记录到达点；不得把模型声明的地面 waypoint 当成塔顶。不会预设新世界的 XYZ、某个平台“必须高多少米”、固定地块数或行走距离。必要时结合侧视画面、可见网格、脚底位置和碰撞接触解释支撑；Raw 缺少 SDK 读数时，仍必须用实际行动证实可观察行为。

### 180–300 秒探索与附件

- 每案至少有一段连续的 180–300 秒主动游玩：从出生区域到主要地点，经过下文的关键路线，探索一个画外或侧向空间并返回/形成完整游览。暂停、加载、站桩等待及反复原地绕圈不计作内容覆盖。时长本身不证明内容充足；记录真正到过的区域、视角变化、岔路与可交互对象。
- 开阔场景允许自由地面探索，不强制编造迷宫或狭窄通道。也不以一个无限平面和稀疏背景贴图满足三分钟目标。新增画外内容应延续原图的坡向、生态、建筑或农田关系。
- 角色转身、跑步、跳跃和重置时，显著附件必须属于同一个受控主体：记录身体与附件的相对位置及可见连接。可有合理的骨骼/摆动形变；不能把附件留在出生点、复制出第二个主体或悄悄换成人形代理。
- 若交付声明运行时缩放、显隐、生成/删除或 NPC 行动能力，按它实际暴露的身份测试，并核对完整对象及碰撞/路线一致性。没有声明的 NPC、战斗、飞行、游泳、天气系统不凭参考图新增成硬性任务；所缺能力单列，不能假称支持。

## 3. 每案冻结的语义目标

### 3.1 海岸灯塔

原图观察：人形旅行者背向镜头位于下半部中央，兜帽、棕色背包和衣服外轮廓显著；左侧是海与远处水平线，前中景有岩石、沙地和浅潮池。崖壁从中景向右上抬升，灯塔及相邻小屋立于右上高地。

- **可见拓扑与首帧必须保留：** 海在左、陆地/崖壁在右，低潮间带与高草地存在真实高差；灯塔仍是右上远端的竖直地标，包含塔身、顶部灯室/平台及邻近建筑的主要体积。岩石/潮池的间隔、前景沙地开口和崖壁轮廓应支撑原图的视线纵深，不能整体变成与主角等深度的一排装饰。
- **关键路线：** 从出生沙地穿过可辨认的潮间带通行空隙，到崖脚或沿岸中景，再经与地形一致的上行连接进入灯塔所在高地的可走区域；观察灯塔近处及侧面后返回。上行入口可位于合理的画外延伸，不规定其世界坐标。
- **支撑与运行重点：** 大岩体应挡路或提供真实可站表面；细小石头/苔藓可为非碰撞装饰。走/跑重复同一段岩石间通路，区分物理阻挡与 Shift 自身断续；不能靠全区关闭碰撞、穿过大岩体或把潮池/崖壁铺成同一高度平面解决通行。
- **探索与边界：** 包含低岸、高岸及沿岸侧向探索，不能只在出生沙地等待三分钟。浅水支撑与远海分开：可以限制进入深水，但不能把海面当成无差别平地一路行走。灯塔室内、塔顶、游泳和动态潮汐不是本案额外硬门槛。

### 3.2 森林瞭望塔

原图观察：橙色背心、持地图的人形主体在前景中央；前左有指示牌，路径朝左前的高架瞭望塔分岔，右侧有带栏门的下坡路。瞭望塔有开放的支腿/交叉支撑、左侧梯子、上部环绕平台与带屋顶观察室；塔旁有水罐/棚屋，右后方是开阔山谷。

- **可见拓扑与首帧必须保留：** 塔在主体左前且高于地面，右侧山谷保持开阔纵深；塔腿之间应有可识别空隙，平台、栏杆、房体、屋顶、梯子形成一个完整地标。指示牌与右侧栏门/分路保留其相对位置。不能把高塔缩成地面小亭或用一块悬空板替代完整塔体。
- **硬性关键路线：** 出生点 → 林地岔路 → 塔的实际上行入口 → **上部平台的可站地板** → 在平台停步/转向/观察 → 下降回到地面。只走到塔脚、与平台 XZ 重合或截图从空中俯看不算登塔。
- **上行行为：** 图中的梯子/上台连接应可用。允许受输入控制的连续攀爬，或保留可见梯子关系的合理阶梯/坡道接入；不得瞬移到顶、在任意位置按键升空、穿过平台、修改出生点到高层。攀爬在中途暂停、离开攀爬区域或到平台交接处必须有清楚且一致的行为。
- **支撑与侧路：** 登台后脚底应由平台实际支撑，不能悬在地板下方或穿过地板。回到地面后探索右侧下坡/山脊方向和一条林地侧路；栏门若挡住路线，须有明确通行方式或可见绕行空隙，不能穿栏替代连接。树干、草和碎石的碰撞密度不能封死原图开阔空地。
- **探索与边界：** 三分钟内容须覆盖地面、塔上和侧向山脊/林地。远山烟雾和牌中文字可以简化；不强制进入观察室内部，不从路牌“车辆”文字新增驾驶玩法。

### 3.3 纸月宫殿

原图观察：深色披风人形位于近景桥中央；桥面、两侧栏杆和近大远小的灯笼向远处收束，通路进入多层亭台/桥阶。主宫殿位于中央高处，后有巨大月轮；两侧为山体、亭阁与垂落的瀑布，整体有很强的上下层和前后纵深。

- **可见拓扑与首帧必须保留：** 中央人物/桥的引导关系、前景栏杆和灯笼遮挡、曲桥或转折连接、中层亭台、上方主宫殿和背后月轮。宫殿须有可辨识的主体、层叠屋顶/台基和真实厚度；主要建筑/山体不能全部成为一张平面或同高盒子。纸白/灰与暖灯、深色人物的主要对比应可识别，也允许明确的语义配色。
- **关键路线：** 沿前景桥进入中景连接，实际跨过桥与台阶/平台的接缝，经过至少一个转折与可见层级变化，到达主宫殿所在结构的可走外部接入区域；再进入其侧后方或另一条连通的亭台/桥路径，侧向验证建筑厚度。
- **支撑与遮挡重点：** 桥面不能靠隐藏大地板托住整个山谷；偏离桥边/跨层处不应继续在空气中行走。桥端、转角、台阶和栏杆通行净空需适配完整角色，灯笼不能无意封住唯一通道。相机应能通过这些连接而不持续陷入栏杆/大灯笼。
- **探索与边界：** 180–300 秒中应体验桥、不同层级和侧后空间；不能只在一小段前景桥重复走动。允许合理补全被遮挡的步行连接，不要求所有屋顶、尖塔、月轮、远山或瀑布顶部可达，也不凭空要求飞行和宫殿室内剧情。

### 3.4 梯田山谷

原图观察：戴草帽、深色上衣的人形站在前景浅水田中；水田和田埂以弯曲轮廓分层。近右高地明显升起，左前/左中景较低且有小屋、树木，远处山谷与雾中山脊层层后退。

- **可见拓扑与首帧必须保留：** 曲线田埂、田面水区与作物分布、真实的挡土边/层级差，近右高、左远低的非对称关系，以及小屋与远山的纵深。不能用平面上的同心色条、透明水片或孤立矮墙冒充整片多层梯田。
- **关键路线：** 从出生水田到最近可走田埂，经可识别连接到明显更高的田埂/田面，再到另一个层级或相邻连通田区；探索朝左侧小屋/山谷方向的支路，并完成上下行返回。连接可为田埂开口、台阶或坡道，不规定新场景坐标或每层米数。
- **支撑与运行重点：** 在各层停步并侧看脚底位置，确认站立高度随实际田面变化；记录上、下行的高度方向和连通。不能让角色始终在一张水平碰撞底板上穿过可见挡土边。湿田中的脚底可低于水面，但应由合理的泥地支撑，不能把水面渲染当成游泳或漂浮能力证明。
- **探索与边界：** 田埂要能容纳角色与转弯，岔路不能只连到虚假的导航标记。远山/不可见农舍内部不作可达门槛；不要求游泳、种植系统或每一株稻草碰撞。三分钟应包含不同层级与不同视角的田区，而非在单一田面站桩。

### 3.5 九尾狐麦田

原图观察：一个白色狐狸坐在前景小路上，头部向画面右侧回转；尖耳、口鼻、胸颈、四足身体/坐姿及铺展的大尾部共同构成主体。九尾呈宽大扇形覆盖下半幅两侧。小路向中央远处圆形石台延伸，麦田中有环形纹路/通道，远山与夕阳形成水平背景。

- **完整主体硬门槛：** 控制的必须是同一只狐狸，具有可辨识的狐狸头身、四肢和**九条**尾部形态；不能换成人形、多个并排动物、裸胶囊或只给静态尾巴后面移动一个替身。九条尾巴可为一个网格/骨架，不要求九个独立 Mesh；单一首帧可有遮挡，但通过三视图/绕看应能核验九条尾部与身体的关系。
- **首帧必须保留：** 坐姿与向画面右侧回头的主要关系，主体在近景的尺度、白狐与金色麦田的区分，尾部左右铺展的宽大轮廓及其前景遮挡。不能机械套用直立人形正后视角或把全部尾巴缩成一个小团。主路、中央圆台和环形麦田保持轴向与远近关系。
- **移动/附件硬门槛：** 前进离开出生位置、左右转向、跑步、跳跃及重置时，整只狐狸与九尾保持共同身份和连接；从后方回看出生点，不能留下尾巴、耳朵或胸毛“道具”。允许尾巴有合理的柔性摆动或简化运动。首帧坐姿与后续四足移动表现分别检查；若只能坐姿整体滑行，明确记录运动还原降级，不能称四足运动表现通过。
- **关键路线：** 从出生小路沿可见主通道到圆形石台附近，沿环形通道绕看，并探索相邻麦田/另一段环路后返回。圆台应有可辨识厚度及侧面；若声明可登台，必须实际上台、停步、下台，不能用贴地圆形颜色区域代替石台。
- **支撑、相机与探索：** 宽尾可穿过柔软麦穗，不能因此把整只狐的碰撞做成封死通道的大墙。狐狸身体要在地面稳定移动，大尾部转向后镜头仍应可玩；长时间穿入石台等硬体须记录为可见缺陷。环路与场景纵深须支撑三分钟实际游览；不额外要求战斗、法术、飞行、毛发物理或迷宫解谜。

## 4. 外部执行与证据记录

1. 核对 case、reference/prompt hash、profile、模型/推理强度、runtime lock、sourceHash、worldBuildHash、episodeHash、归档 SHA 和文件闭包。输入错配先停止质量比较；有效的失败产物与诊断仍保留。
2. 保存真实重置首帧；先用本计划及原图判主体、构图和可见拓扑，再查看生成方的“成功”标签或路线自评。接近/绕看完整主体与地标，检查三视图方位及真实厚度。
3. 审阅者独立标记本案语义目标和支撑面，保存目标解释后进行操作。标记来自“塔上平台地板”等可见对象，不来自模型给出的容易到达点；缺少目标本身即失败，不能改成近旁地面。
4. 做连续输入和生命周期检查，再进行上述 180–300 秒关键路线/探索；记录真实按键与原始视频。自动脚本只能发送同类真实输入，不允许传送、改碰撞、改生成源码、直接修改角色坐标完成目标。
5. 发生卡住、坠落、附件脱离、跑步断续或运行时停止时，保存触发前后画面、输入、位置/高度、可用的时钟/错误/接触/clip 读数。分别归因输入、相机、几何、支撑、SDK/作者代码或证据缺失；没有证据时标不确定，不猜“Shift坏了”或“就是石头”。
6. 报告逐项结果及重现步骤，区分已确认缺陷与未覆盖项。修复后的新 source/runtime 必须有新证据；原始失败记录不得删除。暂停/重置相关的重复测试使用明确新起点，不能把不同版本的图、视频和运行快照拼成同一次通过。

建议每个 case 的外部记录含：输入/产物身份、上述八项结果、原图锚点说明、语义目标说明、真实操作/视频路径、关键高度与角色附件证据、缺陷触发步骤、能力缺口、复验所对应的新版本。若视频/快照缺失，相关维度为 `not-verified`，不能由口述补成通过。

## 5. 对照范围与解释限制

- 固定这五案，失败不换题。两个 profile 使用同一原图、共同业务 prompt、模型/推理强度、预算规则、输入工具和这份外部验收标准；分别保留允许不同的指南、资产加载便利、物理/导航和控制端口等辅助内容。
- `three-raw` 与 `three-sdk` 比较的是**整套辅助工作流**。SDK 包含已写好的输入、物理、导航、资产处理和世界控制，Raw 需要作者自行实现相应行为；本轮不能把差异单独归因于 API 命名或“加 SDK 必然提升/降低 GPT-6 能力”。
- SDK 特有的内部读数可以增强解释，但不得让 Raw 因没有 SDK 私有字段而自动失败；共同的可观察玩法与原图要求仍须同样检查。也不能因为 SDK 能上报 reached/grounded 就免除真实登塔、跨层和附件跟随检查。
- 报告每案原始结果、耗时/工具反馈与具体缺陷，区分技术链路成功和语义成功。五案是有目的的小样本，覆盖场景类型有限；不估计总体成功率，不外推任意第一人称、室内、载具、飞行、游泳或大规模 NPC 能力。
- 本次只验可玩的白模及其原始视频/三视图。实时视频模型的最终视觉质量、延迟和 prompt 控制分工需要另行实测，不能由白模通过推断。
