# Three SDK 设计与职责

## 设计背景与取舍

团队在实际使用中观察到，GPT-6 Astra 熟悉 Three.js 原生代码，具有较强的空间
多模态理解与 3D 场景还原能力，能快速完成场景构建。这是从原有复杂、沉重的
Babylon + SDK 方案转向普通 Three 创作与轻量 SDK 的业务依据。

让 AI 发挥已有能力：自主还原构图、搭建 Mesh/Group、安排可通行的空间连接、
编写场景逻辑、配置碰撞体与交互锚点。避免要求作者先学习另一套场景语言，
也不将通用场景构造 API 的完整性作为 SDK 建设目标。

SDK 集中投入 AI 难以稳定完成且值得复用的能力，例如预设人物模型、骨骼绑定、
动作与骑乘组合，以及物理、动画、相机和生命周期的稳定执行。作者决定场景和
碰撞描述，已有运行时负责执行；保持每项状态一个写入者，避免重复模拟。
轻量化关注创作约束与接入负担，核心预设仍需可靠。

新增 API、重构或校验时，使用以下判断原则：

- 优先修复合法输入消费不一致、能力描述失真、单位与行为不符、无效字段及
  工具契约差异，减少 Agent 无意义的猜测和重试。
- 优先补准确说明、当前有效能力和最小示例。原生 Three 已能清楚表达的工作，
  保留给 AI；真实案例反复出现相同困难时，再提取窄范围的公共能力。
- 当前项目尚未上线，以当前契约同步修改 SDK、Host、示例和测试。不为未发布的
  旧版项目保留兼容分支、重复解析或降级适配；确有上线消费者后再按实际需求设计。
- 新增抽象须服务实际需求。API 对称、分类齐全、统一所有控制方式或文件结构
  更整齐，本身不足以支持增加框架、包装层或配置体系。
- 生成链路保持必要的执行与交付契约，优先通过 Harness 反馈帮助 Agent 发现并
  修正问题。新增强制门禁或预演须有明确的失败依据与收益，遵循下述反馈原则。
- 以生成效果、成功率、返工次数、工具调用和耗时衡量收益，避免用新增接口、
  校验条目或抽象层数衡量工程质量。维护 SDK 的开发测试与每次生成必须执行
  的步骤分别考虑，不把维护者的完整回归要求变成生成 Agent 的固定流程。

场景无法枚举。给 Agent 提供 SDK 能力、参数单位、默认值、绑定方法和真实执行条件，
由 Agent 根据需求与参考决定场景内容以及是否使用某项能力。示例说明用法，不能变成
固定物体类别、场景组成或可选功能的必选清单。SDK 能力类型可以有限，场景组合不受
示例或资产目录枚举限制。

以上取舍指导维护者决策。给生成 Agent 的说明保持直接：可用能力、实际契约、
必要条件和示例；不额外要求它执行一轮架构论证或自我限制流程。

## 内部配置与调参

SDK 的维护者调参表集中在 `packages/three-world/src/config/`，按移动、镜头、动作、
输入、物理和展示效果分文件。以 Playground 的实际标定表现为基准，SDK 与
Playground 共同读取这份定义；Host 账号、权限与生产配置仍归仓库根 `config/`。

- 配置描述默认值、范围、单位、适用控制器和已有能力的开关；执行逻辑留在各自
  模块。不建立通用配置中心、可变全局注册表或新的场景语言。
- 默认表只读，每个运行时持有自己的配置副本。内部效果开关由开发人员修改后
  重新构建，不作为新的 Agent profile 字段；已有公开调参能力继续按原 owner 应用。
- 保存配置与生效配置分别表达。`exportProfile()` 用于重放；`inspectConfiguration()`
  按当前主体与模式提供解析结果，并标明相机控制权。读取不推进模拟。
- 参数定义、SDK/Host schema、Playground 字段和适用范围共享来源。当前完整保存
  表单不做旧版迁移；运行时已有局部覆盖仍可用。不因家族暂不消费某字段新增生产门禁。
- 镜头侧倾继承与车辆物理姿态分开配置。关闭镜头横滚不能清零车身旋转，也不能
  改变眼位、视线、碰撞或固定时钟。

具体文件归属与修改方式见 [SDK 配置说明](../packages/three-world/src/config/README.md)。

## Harness 反馈与生产校验

**生产校验保持克制，反馈能力持续增强。** Harness 是围绕实际执行提供观察、
诊断与结果反馈的支撑层，帮助 Agent 理解“现在是什么状态、操作发生了什么、
哪里与预期不同”，再自主调整作品。避免靠不断叠加严格门禁来代替这一闭环；
门禁的误报、阻断和重试也会降低端到端成功率并增加耗时。

反馈不限于页面截图或三视图。按实际问题提供以下信息；这是建设方向，具体
已实现能力以 SDK 与 Host 的真实工具契约为准，不要求每个世界实现全部观测项。

| Agent 需要理解什么 | 可提供的反馈 |
| --- | --- |
| 画面与空间关系 | 主视角、三视图、局部视角、关键帧、短录像，以及按需的碰撞体或交互锚点叠加图 |
| 当前执行状态 | 实际控制主体、输入与控制权、相机模式、位置速度、接触与支撑、动作阶段及可用条件 |
| 操作是否奏效 | 请求是否开始/完成、前后状态变化、实际位移、碰撞或拒绝原因、相关对象与发生位置 |
| 运行与交付为何异常 | 加载/编译/浏览器错误、阶段进度、必要的耗时信息、实际产物与缺失项 |

反馈接口遵循以下原则：

- **按需可查，默认简短。** 让 Agent 在需要时查询最新可观测状态；默认给摘要、
  关键变化和相关对象，细节、长日志或高成本图像按需获取。复用已有采样与证据，
  不把每步全量采集、持续高频轮询或额外模型调用变成必经流程。
- **事实可追溯。** 状态、图像与执行结果关联到相应任务、源码/运行时版本和
  采样时刻或模拟帧。区分当前与历史、测量与推断、未知与失败；查询不到或
  诊断自身出错时如实说明，不冒充成功，也不把未知直接判成作品失败。
  带调试叠加的诊断视图与正式交付画面分别标注。
- **反馈支持修正。** 尽量返回具体对象、条件和证据，让 Agent 能采取下一步
  行动。错误码可辅助定位，不能只有笼统的“未通过”；给出建议不自动改写场景、
  放宽碰撞或动作资格，也不伪造执行证据。
- **观测与阻断分开。** 仅将确有必要的执行与交付条件设为阻断项；效果判断、
  启发式风险和诊断建议优先作为反馈。辅助观测失败应局部降级；只有确实影响
  执行或必需交付证据时才阻断。增加检查前考虑成本、误报和重试代价，不能因
  “可以检查”就要求每次生产必须通过。
- **观测不接管执行。** 从已有 SDK/Host 读取真实状态，普通观察不推进模拟或
  留下输入、相机和物理状态变更；展示所需的临时变更由捕获事务恢复。
  需要实际执行的试探应明确其动作与范围，复用
  同一运行时，不额外创建模拟循环或用推断状态替代真实状态。

工程验证也按改动影响选择：用相关测试证明必要行为，已通过且源码未变的检查
不反复重跑；运行时关键改动仍验证实际受影响的输入、生命周期与 Creator/Episode
消费者。以反馈能否减少定位时间、返工和失败来衡量价值，避免追求日志数量或
检查项覆盖率本身。本节不新增生成步骤或门禁。

## 创作目标

目标是让 Agent 创建简洁可玩的白模，用户自然操作，并让 Episode 记录同一套动作，
供后续样式与视频数据生产使用。环境使用白色、浅灰基本体块和均匀基础照明；
少量关键标志物、交互目标加识别色。保留大体构图、尺度、空间关系和真实碰撞条件。
先按需求确定被控制的主体；动物或其他非人主角直接作为主体，不额外添加人或骑手。
Creator 生成中的所有人形（含 NPC 和骑手）使用许可的预设人物，当前为
`humanoid.source-101`，保留可见模型、骨架和动作，不添制服装或配饰。
每个人物在步行、上车、骑乘、下车和重置中保持同一实例；不能隐藏原人物，
或把自绘骑手塞进载具模型。主体外形、运动能力与骑乘关系分别描述，以实际控制器
和资产条件为准。非人形生物优先复用提供的资源。车辆外观由 Agent 自绘，
不使用预设或外部车辆模型：先按操控方式选择不含模型的车辆配置，再依据其
轮组、物理尺寸、碰撞范围和座位锚点绘制 Mesh，通过 SDK 载具接口组合。
当前汽车与摩托使用 `training.createRoadVehicleSpec`；轮胎动画读取 SDK 的
同一份显示采样。配置不创建模型、物理世界或额外控制循环。
省去装饰细节、氛围、反射和复杂阴影，创作精力用于可玩功能。

## 四层使用方式

| 层级 | Agent 的工作 | 入口与结果 |
| --- | --- | --- |
| 直接复用 | 按主体选择入口与能力 | 独立主体 `createWorld`；完整人物 `createHumanoidWorld` |
| 场景与能力绑定 | 自制 Mesh；补碰撞、水体、攀爬面、交互锚点 | `TrainingMap`、`TrainingVehicleInstance`；自制地面主体用 `addCharacter` 的 `object/body/movement` |
| 参数配置 | 调速度、加速、滑行和镜头 | 带单位的 profile、movement 与按键配置；导出到项目 |
| 源码实现 | 修改动作、动画、碰撞或控制器 | `creator_materialize_runtime` 后修改项目 SDK 源码，重新编译与验证 |

公开类型与示例见 [SDK README](../packages/three-world/README.md)。同一资产可以复用
外观或完整能力，但一个 clip 名称不代表对应物理能力已接入。自制骨架需要兼容动画
映射；绑定地面移动不会自动产生四足步态或翅膀动画。

## 入口与封装边界

`createWorld` 是通用世界入口，可绑定人形或非人主体，并非非人专用 API。
`createHumanoidWorld` 是完整人物套件的快捷入口：加载或接收人物，绑定既有
人物动作与控制器，可组合独立载具，内部仍调用 `createWorld` 并返回同一种
`ThreeWorld`。两者共享模拟、物理、动画调度、相机和生命周期的执行权。

Creator 的人物、人物骑乘、非人主体三条路线用于选择接入方式，不是三种互斥
的 SDK 实体类型。主体外形、运动能力、能否骑乘和能否被骑乘分别判断；一个
动物既可作为独立主角，也可在另一场景中被骑乘，取决于任务及已接入能力。

当前不增设 `createNonHumanWorld`。非人形态之间没有统一的完整运动套件可供
该名称承诺；复用 `addCharacter`、控制目标、相机跟随、捕获目标和 `start`
即可接入现有能力。若生成案例持续出现相同的绑定遗漏或重复接线，再考虑
通用的可控主体快捷封装，其职责仅是组合已有组件，不自动赋予飞行、游泳、
导航或骨骼动画。避免为 API 形式对称建立新运行时或重复能力配置。

## 动作与输入契约

每张能力卡回答：用途、触发、人物条件、场景条件、参数、完成状态、失败原因和
源码入口。`training.characterCapabilities()` 返回实时可用性；动作定义、前置
检查、HUD 和工具说明复用同一份元数据。

例如滑铲由 **Shift + 新按 C/Ctrl** 触发，需要落地、站立、空手、无冲突/冷却、
实际速度至少 2.5 m/s。普通地面可以滑铲；低通道需要真实碰撞和足够助跑距离。
退出头顶空间不足时保持低姿态。详细条件见 SDK `character-actions` 主题。

默认操作是 WASD 移动、Shift 冲刺、Space 跳跃/翻越/起身、C/Ctrl 蹲伏、Z 匍匐、
Q 翻滚、E 交互、G 放下、F 上下载具。控制表统一生成提示和录制可用按键；
用户可以重绑，Agent 使用语义输入或动作请求。E 优先选择当前交互目标，再尝试
攀爬。动画过渡不分配独立按键。

Agent 读取动作可用性与目标位置，先通过真实输入接近，再提交动作。`accepted`
表示开始，最终操作状态和 snapshot 决定是否完成。碰撞、拒绝和超时也进入证据。

## 执行职责

| 内容 | 唯一执行者 | 作者可以修改什么 |
| --- | --- | --- |
| 外观与场景 | 普通 Three.js | Mesh、Group、材质、光照、视觉子对象 |
| 物理、支撑与重力 | SDK 选定的 Rapier 后端 | 碰撞描述、参数或该模块源码 |
| 角色运动与动画 | SDK 角色控制器和动画模块 | 输入、动作配置、兼容绑定或模块源码 |
| 镜头 | 当前相机模式的写入者 | 初始构图、跟随参数、模式或模块源码 |
| 模拟与生命周期 | SDK 固定时钟 | 通过 start/stop/reset/commands 操作 |
| UI、模型输入/输出 | Presentation 和应用 | HTML UI、传输和真实源帧映射 |
| 编译、自检与交付 | Creator Host | 项目源码；Host 验证不属于作品运行时 |
| 规划、录制、样式 | Episode Host 与阶段 Agent | 动作目标、路线、样式计划 |

修改底层是在项目运行时构建内替换对应模块，仍保持每项状态一个写入者。
场景代码不额外创建物理世界、模拟循环或相机跟随。运行时源码与实际字节共同进入
交付身份，便于复验与独立消费。

### 相机控制权与交接

普通世界与 Training 保留各自构图、人物可见性和物理过滤策略，通过查询适配器
调用 `camera-collision` 的同一套支点分离、回缩、恢复与镜头轨迹检测。每个控制器
独立持有求解状态；上下马、模式切换、地图变更和重置清理不兼容的历史状态。

`solve` 只由固定步进或显式的零时间生命周期同步调用；显示插值使用不读写恢复
状态的 `project`，紧急回退位置也必须来自固定快照。重复显示与截图不能推进恢复
计时或影响下一固定步进。局部遮挡可保留构图，但镜头本身进入几何体必须避让。

- 主相机同一时刻只有一个控制者。作者构图与 SDK 跟随模式显式交接；普通世界
  与 Training 的跟随执行路径互斥，步行与骑乘由同一个 Training 相机切换目标。
  场景、Playground UI 和录制工具通过受支持的接口提交意图，不另建持续写入主相机的循环。
- 固定步进求解相机，显示阶段从同一份状态历史取样。显示取样不推进模拟、阻尼
  或输入状态；插值产生的新镜头位置复用所属相机的可见性与碰撞规则，不能用另一套
  通用遮挡策略覆盖已求解的构图。碰撞辅助模块提供计算结果，不独立接管主相机。
- Creator 通过同步展示事务捕获画面；对象三视图使用临时相机，并恢复临时改变的
  场景和渲染器状态。Episode 独占录制时钟，停用实时循环并拒绝冲突的普通控制；
  捕获、释放和重置均不能留下第二条相机更新路径。

## 画面与生产

`world.createPresentation()` 将纯世界输入、模型输出和 DOM UI 分开。模型返回
真实源帧身份后，HUD 才能对应历史状态；未知映射不能靠猜测固定延迟补齐。
重置使源帧身份失效。

Creator 用完整的真实输入计划覆盖核心功能及动作结果，录制长度由覆盖需要决定。
提交包含自检录像、开场、重要对象三视图和源码/运行时身份。
Episode 在独立生产副本中，用同一 SDK 记录六段 30 秒动作，之后制作十套风格。
录制中每帧来自真实模拟，动作事件来自执行证据。视频请求准备完成与最终视频完成
分别表达；执行范围见 [数据生产](three-sdk-data-production.md)。

## 验证

先检查接口消费者和场景条件，再验证真实输入、动作转换、失败结果、reset 和录制。
Creator 和 Episode 都要验证，某一侧通过不替代另一侧。运行时检查见
[专项检查表](reviews/runtime-deep-review-checklist.md)；纯文档检查链接、声明和
schema 主题提取。云任务、部署和外部审核依照实际任务授权执行。
