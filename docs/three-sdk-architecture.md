# Three SDK 设计与职责

## 设计背景与取舍

团队在实际使用中观察到，GPT-6 Astra 熟悉 Three.js 原生代码，具有较强的空间
多模态理解与 3D 场景还原能力，能快速完成场景构建。这是从原有复杂、沉重的
Babylon + SDK 方案转向普通 Three 创作与轻量 SDK 的业务依据。

让 AI 发挥已有能力：自主还原构图、搭建 Mesh/Group、安排可通行的空间连接、
编写场景逻辑、配置碰撞体与交互锚点。避免要求作者先学习另一套场景语言，
也不将通用场景构造 API 的完整性作为 SDK 建设目标。

SDK 集中投入 AI 难以稳定完成且值得复用的能力，例如预设人物模型、骨骼绑定、
动作与骑乘组合，以及物理、动画、相机和生命周期的稳定执行。作者决定场景和
碰撞描述，已有运行时负责执行；保持每项状态一个写入者，避免重复模拟。
轻量化关注创作约束与接入负担，核心预设仍需可靠。

新增 API、重构或校验时，使用以下判断原则：

- 优先修复合法输入消费不一致、能力描述失真、单位与行为不符、无效字段及
  工具契约差异，减少 Agent 无意义的猜测和重试。
- 优先补准确说明、当前有效能力和最小示例。原生 Three 已能清楚表达的工作，
  保留给 AI；真实案例反复出现相同困难时，再提取窄范围的公共能力。
- 当前项目尚未上线，以当前契约同步修改 SDK、Host、示例和测试。不为未发布的
  旧版项目保留兼容分支、重复解析或降级适配；确有上线消费者后再按实际需求设计。
- 新增抽象须服务实际需求。API 对称、分类齐全、统一所有控制方式或文件结构
  更整齐，本身不足以支持增加框架、包装层或配置体系。
- 生成链路保持必要的执行与交付契约，优先通过 Harness 反馈帮助 Agent 发现并
  修正问题。新增强制门禁或预演须有明确的失败依据与收益，遵循下述反馈原则。
- 以生成效果、成功率、返工次数、工具调用和耗时衡量收益，避免用新增接口、
  校验条目或抽象层数衡量工程质量。维护 SDK 的开发测试与每次生成必须执行
  的步骤分别考虑，不把维护者的完整回归要求变成生成 Agent 的固定流程。

场景无法枚举。给 Agent 提供 SDK 能力、参数单位、默认值、绑定方法和真实执行条件，
由 Agent 根据需求与参考决定场景内容以及是否使用某项能力。示例说明用法，不能变成
固定物体类别、场景组成或可选功能的必选清单。SDK 能力类型可以有限，场景组合不受
示例或资产目录枚举限制。

以上取舍指导维护者决策。给生成 Agent 的说明保持直接：可用能力、实际契约、
必要条件和示例；不额外要求它执行一轮架构论证或自我限制流程。

## 内部配置与调参

SDK 的维护者调参表集中在 `packages/three-world/src/config/`，按移动、镜头、动作、
输入、物理和展示效果分文件。以 Playground 的实际标定表现为基准，SDK 与
Playground 共同读取这份定义；Host 账号、权限与生产配置仍归仓库根 `config/`。

- 配置描述默认值、范围、单位、适用控制器和已有能力的开关；执行逻辑留在各自
  模块。不建立通用配置中心、可变全局注册表或新的场景语言。
- 默认表只读，每个运行时持有自己的配置副本。内部效果开关由开发人员修改后
  重新构建，不作为新的 Agent profile 字段；已有公开调参能力继续按原 owner 应用。
- 保存配置与生效配置分别表达。移动 profile 用 `exportProfile()` / `inspectConfiguration()`；
  镜头文档与实际状态用 `inspectCamera()`，并区分配置、提交和生命周期版本。读取不推进模拟。
- 参数定义、SDK/Host schema、Playground 字段和适用范围共享来源。当前完整保存
  表单不做旧版迁移；运行时已有局部覆盖仍可用。不因家族暂不消费某字段新增生产门禁。
- 镜头侧倾继承与车辆物理姿态分开配置。关闭镜头横滚不能清零车身旋转，也不能
  改变眼位、视线、碰撞或固定时钟。

具体文件归属与修改方式见 [SDK 配置说明](../packages/three-world/src/config/README.md)。

## Harness 反馈与生产校验

**生产校验保持克制，反馈能力持续增强。** Harness 是围绕实际执行提供观察、
诊断与结果反馈的支撑层，帮助 Agent 理解“现在是什么状态、操作发生了什么、
哪里与预期不同”，再自主调整作品。避免靠不断叠加严格门禁来代替这一闭环；
门禁的误报、阻断和重试也会降低端到端成功率并增加耗时。

反馈不限于页面截图或三视图。按实际问题提供以下信息；这是建设方向，具体
已实现能力以 SDK 与 Host 的真实工具契约为准，不要求每个世界实现全部观测项。

| Agent 需要理解什么 | 可提供的反馈 |
| --- | --- |
| 画面与空间关系 | 主视角、三视图、局部视角、关键帧、短录像，以及按需的碰撞体或交互锚点叠加图 |
| 当前执行状态 | 实际控制主体、输入与控制权、相机模式、位置速度、接触与支撑、动作阶段及可用条件 |
| 操作是否奏效 | 请求是否开始/完成、前后状态变化、实际位移、碰撞或拒绝原因、相关对象与发生位置 |
| 运行与交付为何异常 | 加载/编译/浏览器错误、阶段进度、必要的耗时信息、实际产物与缺失项 |

反馈接口遵循以下原则：

- **按需可查，默认简短。** 让 Agent 在需要时查询最新可观测状态；默认给摘要、
  关键变化和相关对象，细节、长日志或高成本图像按需获取。复用已有采样与证据，
  不把每步全量采集、持续高频轮询或额外模型调用变成必经流程。
- **事实可追溯。** 状态、图像与执行结果关联到相应任务、源码/运行时版本和
  采样时刻或模拟帧。区分当前与历史、测量与推断、未知与失败；查询不到或
  诊断自身出错时如实说明，不冒充成功，也不把未知直接判成作品失败。
  带调试叠加的诊断视图与正式交付画面分别标注。
- **反馈支持修正。** 尽量返回具体对象、条件和证据，让 Agent 能采取下一步
  行动。错误码可辅助定位，不能只有笼统的“未通过”；给出建议不自动改写场景、
  放宽碰撞或动作资格，也不伪造执行证据。
- **观测与阻断分开。** 仅将确有必要的执行与交付条件设为阻断项；效果判断、
  启发式风险和诊断建议优先作为反馈。辅助观测失败应局部降级；只有确实影响
  执行或必需交付证据时才阻断。增加检查前考虑成本、误报和重试代价，不能因
  “可以检查”就要求每次生产必须通过。
- **观测不接管执行。** 从已有 SDK/Host 读取真实状态，普通观察不推进模拟或
  留下输入、相机和物理状态变更；展示所需的临时变更由捕获事务恢复。
  需要实际执行的试探应明确其动作与范围，复用
  同一运行时，不额外创建模拟循环或用推断状态替代真实状态。

工程验证也按改动影响选择：用相关测试证明必要行为，已通过且源码未变的检查
不反复重跑；运行时关键改动仍验证实际受影响的输入、生命周期与 Creator/Episode
消费者。以反馈能否减少定位时间、返工和失败来衡量价值，避免追求日志数量或
检查项覆盖率本身。本节不新增生成步骤或门禁。

## 创作目标

目标是让 Agent 创建简洁可玩的白模，用户自然操作，并让 Episode 记录同一套动作，
供后续样式与视频数据生产使用。还原参考图片的样式与主要形态，简化细节；
世界整体以白色为主，仅使用均匀基础照明。
主体、关键客体和标识物用少量不同的识别色区分，并选入三视图，实景与各视图
保持同一对象颜色一致。地面、水面等地形用轻微灰度或色调差区分，普通布景保持
中性白灰。保留大体构图、尺度、空间关系和真实碰撞条件。
先按需求确定被控制的主体；动物或其他非人主角直接作为主体，不额外添加人或骑手。
Creator 生成中的所有人形（含 NPC 和骑手）使用许可的预设人物，当前为
`humanoid.uefn-mannequin`，保留可见模型、骨架和动作，不添制服装或配饰。
每个人物在步行、上车、骑乘、下车和重置中保持同一实例；不能隐藏原人物，
或把自绘骑手塞进载具模型。主体外形、运动能力与骑乘关系分别描述，以实际控制器
和资产条件为准。非人形生物优先复用提供的资源。车辆外观由 Agent 自绘，
不使用预设或外部车辆模型：先按操控方式选择不含模型的车辆配置，再依据其
轮组、物理尺寸、碰撞范围和座位锚点绘制 Mesh，通过 SDK 载具接口组合。
当前汽车与摩托使用 `humanoid.createRoadVehicleSpec`，轻型固定翼使用
`humanoid.createAircraftSpec('plane')`；固定翼须匹配返回的固定 airframe 标定，
该字段不是任意机型的物理覆盖。轮胎动画读取 SDK 的
同一份显示采样。配置不创建模型、物理世界或额外控制循环。
省去装饰细节、氛围、反射和复杂阴影，创作精力用于可玩功能。

地形、构图、标识物、主体和客体必须以参考图为依据，保留主要形态、尺度与空间关系。
可见模型独立绘制；碰撞体描述支撑、阻挡和动作净空，空气墙只参与物理，不生成实体围墙。
用户 Prompt 未要求玩法时，只提供参考世界中的自由移动和探索；要求玩法时，实现对应
需求。自检路径、捕获目标和三视图标识物不自动成为玩家任务，不添加未要求的观测、
打卡、答题、收集或障碍关卡。

正常速度下应有至少 5 分钟的参考场景探索空间；这是空间容量，不要求增加玩法。
容量估算与实测时长分别说明，不靠空跑、降速或等待凑时，不规定自检录像时长。
Creator 验证实际可通行性、运动、镜头及用户要求的功能，复用真实输入、状态和画面。
详细说明见 [Creator 质量指引](../packages/creator-host/README.md#exploration-and-quality)。

## 四层使用方式

| 层级 | Agent 的工作 | 入口与结果 |
| --- | --- | --- |
| 直接复用 | 按主体选择入口与能力 | 独立主体 `createWorld`；完整人物 `createHumanoidWorld` |
| 场景与能力绑定 | 自制 Mesh；补碰撞、水体、攀爬面、交互锚点 | `EnvironmentDefinition`、`VehicleInstance`；自制地面主体用 `addCharacter` 的 `object/body/movement` |
| 参数配置 | 调速度、加速、滑行和镜头 | 带单位的 profile、movement 与按键配置；导出到项目 |
| 源码实现 | 修改动作、动画、碰撞或控制器 | `creator_materialize_runtime` 后修改项目 SDK 源码，重新编译与验证 |

公开类型与示例见 [SDK README](../packages/three-world/README.md)。同一资产可以复用
外观或完整能力，但一个 clip 名称不代表对应物理能力已接入。自制骨架需要兼容动画
映射；绑定地面移动不会自动产生四足步态或翅膀动画。

## 入口与封装边界

`createWorld` 是通用世界入口，可绑定人形或非人主体，并非非人专用 API。
`createHumanoidWorld` 是完整人物套件的快捷入口：加载或接收人物，绑定既有
人物动作与控制器，可组合独立载具，内部仍调用 `createWorld` 并返回同一种
`ThreeWorld`。两者共享模拟、物理、动画调度、相机和生命周期的执行权。

Creator 的人物、人物骑乘、非人主体三条路线用于选择接入方式，不是三种互斥
的 SDK 实体类型。主体外形、运动能力、能否骑乘和能否被骑乘分别判断；一个
动物既可作为独立主角，也可在另一场景中被骑乘，取决于任务及已接入能力。

当前不增设 `createNonHumanWorld`。非人形态之间没有统一的完整运动套件可供
该名称承诺；复用 `addCharacter`、控制目标、相机跟随、捕获目标和 `start`
即可接入现有能力。若生成案例持续出现相同的绑定遗漏或重复接线，再考虑
通用的可控主体快捷封装，其职责仅是组合已有组件，不自动赋予飞行、游泳、
导航或骨骼动画。避免为 API 形式对称建立新运行时或重复能力配置。

## 动作与输入契约

每张能力卡回答：用途、触发、人物条件、场景条件、参数、完成状态、失败原因和
源码入口。`world.humanoid.characterCapabilities()` 返回实时可用性；动作定义、前置
检查、HUD 和工具说明复用同一份元数据。

例如滑铲由 **Shift + 新按 C/Ctrl** 触发，需要落地、站立、空手、无冲突/冷却、
实际速度至少 2.5 m/s。普通地面可以滑铲；低通道需要真实碰撞和足够助跑距离。
退出头顶空间不足时保持低姿态。详细条件见 SDK `character-actions` 主题。

默认操作是 WASD 移动、Shift 冲刺、Space 跳跃/翻越/起身、C/Ctrl 蹲伏、Z 匍匐、
Q 翻滚、E 交互、G 放下、F 上下载具。控制表统一生成提示和录制可用按键；
用户可以重绑，Agent 使用语义输入或动作请求。E 优先选择当前交互目标，再尝试
攀爬。动画过渡不分配独立按键。

Agent 读取动作可用性与目标位置，先通过真实输入接近，再提交动作。`accepted`
表示开始，最终操作状态和 snapshot 决定是否完成。碰撞、拒绝和超时也进入证据。

## 执行职责

| 内容 | 唯一执行者 | 作者可以修改什么 |
| --- | --- | --- |
| 外观与场景 | 普通 Three.js | Mesh、Group、材质、光照、视觉子对象 |
| 物理、支撑与重力 | SDK 选定的 Rapier 后端 | 碰撞描述、参数或该模块源码 |
| 角色运动与动画 | SDK 角色控制器和动画模块 | 输入、动作配置、兼容绑定或模块源码 |
| 镜头 | 当前相机模式的写入者 | 初始构图、跟随参数、模式或模块源码 |
| 模拟与生命周期 | SDK 固定时钟 | 通过 start/stop/reset/commands 操作 |
| UI、模型输入/输出 | Presentation 和应用 | HTML UI、传输和真实源帧映射 |
| 编译、自检与交付 | Creator Host | 项目源码；Host 验证不属于作品运行时 |
| 规划、录制、样式 | Episode Host 与阶段 Agent | 动作目标、路线、样式计划 |

修改底层是在项目运行时构建内替换对应模块，仍保持每项状态一个写入者。
场景代码不额外创建物理世界、模拟循环或相机跟随。运行时源码与实际字节共同进入
交付身份，便于复验与独立消费。

### 相机控制权与交接

普通世界、Humanoid 和载具共用一个 `CameraController`。配置定义在
`config/camera/`：完整 CameraDocument、独立视角策略参数、主体预设快照和解析来源。
主体适配器只提供真实位置、身体、眼位、座位及 generation；策略返回候选姿态，
共享约束层复用 `camera-collision` 的支点分离、回缩与恢复计算。

Agent 用 `world.setCameraFollow({configuration})` 安装完整文档，以
`world.setCameraView(viewId)` 选择声明的视角。开场是视角自己的 opening；
两种第三人称 framing 都使用声明的锚点及偏移；preserve-opening 从原始机位、
朝向和 FOV 推导轨道，look-at 使用声明的距离和俯仰。镜头回正、横滚继承、
速度效果、平滑、碰撞收缩与恢复均由文档独立声明。资产 profile、车辆物理 spec 和地图
不再带入镜头覆盖。具体接入顺序见
[编程规范](../packages/creator-host/docs/agent/programming.md#initial-state-and-camera)。
保存 JSON、应用实时草稿、提交重置基线是三个独立操作；编辑会话检查配置版本和
主体身份，不隐式封存 World。Episode v2 从封存基线读取命名视角和配置身份，
初始化使用 cut，片段内切换遵守过渡；旧格式仅由显式导入边界翻译。

步行人物默认沿水平面背朝最终首帧镜头；`characterFacingYawRadians` 可显式覆盖
（0 朝 −Z，与 Episode 一致）。首帧机位与人物朝向分别配置，一同封存并在重置时
恢复；运行中的镜头移动不重写人物朝向，Episode 显式起点继续由片段控制。

新主体只补数据与必要视角策略，不得绕过公共入口写主相机、监听首次按键重置
镜头或再建时钟。公开跟随参数必须实际消费，不支持的组合明确拒绝。每个新接入
加入同一组公共入口契约测试，覆盖首帧/首次输入/移动/可用主体切换/碰撞恢复/
重置以及 Creator/Episode 捕获；不能只测内部镜头类。资产的坐标、眼位、座位、
视角限制和 Agent 注册方式见 [资产接入规范](asset-production-integration.md#新主体的镜头与输入接入)。

碰撞恢复状态只由固定步进或显式的零时间生命周期同步提交；显示插值使用不读写
恢复状态的 `project`。输入准备直接使用环绕意图生成移动方向，不额外预测碰撞机位。
重复显示与截图不能推进恢复计时或影响下一固定步进。相机臂按笛卡尔坐标柔化；
碰撞安全收近立即执行，回伸通过独立径向状态控制等待、半衰期、死区和速度上限，
不加入眼位空间收近阻尼或角向追赶。自由镜头臂检查移动扫掠，遇到表面时可进行有限次
切向滑动，每段仍检查碰撞及最终占用；受阻镜头臂优先径向修正。
人体构图可在实际胶囊可见、镜头球体未占用时保留机位。原生人物 look-at 第三人称
在遮挡边缘按身体中心视线的球形净空提前收近，避免只剩一点可见时仍保留长臂；
该构图偏好只在固定步计算一次，显示阶段继续执行硬安全约束，不能重复缩臂。
完全遮挡或自由空间不连通时仍优先安全收近，不承诺任意几何都无跳变。数值接触分离与
失败事务回滚由碰撞内核统一处理。详细算法与采样合同见
[碰撞包说明](../packages/camera-collision/README.md)。

第三人称的近距离人物淡出由同一配置中的 subjectFade 声明，仅作用于显示事务。
通用视角默认关闭；原生步行第三人称与越肩预设在 1.2 米内渐隐，0.75 米内隐藏，
作者可显式关闭或覆盖距离。
共享材质保持原样，渲染结束后恢复对象的材质和可见性；Playground、普通场景与
录制共用此行为，第一人称继续使用自身的身体裁剪策略。

策略的轨道基底、相对构图和参考方向随候选姿态传递。look-at 的安全机位使用
`camera/composition.ts` 保持支点与参考地平线，已平滑的参考 up 不能被碰撞修正覆盖；
preserve-opening 沿用作者构图朝向，第一人称保留视线方向。显示阶段插值已提交的
位置与四元数；稳定 look-at/越肩视角的中间样本按插值支点与参考地平线重新定向，
再应用所属策略的安全投影，不反写玩家轨道意图。固定端点、作者构图与混合视角保留各自姿态。
遮挡使安全机位移到支点另一侧时仍保持参考地平线；极点附近保存已应用的瞄准坐标系，
随实际视线移动传递姿态，并在地平线变得明确时恢复参考方向。显示只读取固定样本，
不承诺精确反向视线奇点的全局连续。回归需覆盖
构图、输入方向、重复显示和插值端点，不能只验证机位在碰撞体之外。

输入准备得到的方向只在当前固定步内有效，提交后、后置回调执行前必须释放；
录制和路线控制读取已提交视角的输入方向，不能继续使用预移动缓存。垂直视线的
水平输入方向由镜头自身右轴确定，不回退到固定世界朝向。原生主体显示采样的
位置、旋转、座位和备用眼位必须属于同一显示姿态，包括直接绑定车辆与绑定骑乘
人物两种情况。鼠标/移动与显式选择当前视角共用待激活开场的重基逻辑；切换其他
视角只准入实际所选视角，不因未选中视角的待激活限制而阻断。

- 主相机同一时刻只有一个控制者。作者构图与 SDK 跟随模式显式交接；普通世界
  与 Humanoid 的视角策略都向同一个控制器提交，步行与骑乘只切换主体数据。
  多人物继续共用此控制器；输入角色与镜头目标独立，切换镜头不转移已接受动作。
  场景、Playground UI 和录制工具通过受支持的接口提交意图，不另建持续写入主相机的循环。
- 固定步进求解相机，显示阶段从同一份状态历史取样。显示取样不推进模拟、阻尼
  或输入状态；插值产生的新镜头位置复用所属相机的可见性与碰撞规则，不能用另一套
  通用遮挡策略覆盖已求解的构图。碰撞辅助模块提供计算结果，不独立接管主相机。
- Creator 通过同步展示事务捕获画面；对象三视图使用临时相机，并恢复临时改变的
  场景和渲染器状态。Episode 独占录制时钟，停用实时循环并拒绝冲突的普通控制；
  捕获、释放和重置均不能留下第二条相机更新路径。

### 相机扩展维护规范

相机模块的当前职责、固定步与展示阶段边界、可重复的验收步骤见[相机职责与回归验收](camera-maintenance.md)。

本节是维护者和开发 Agent 扩展相机的权威入口。现有实现支持命名视角、主体绑定、
分层参数、显式 `setCameraView(viewId)` 和可选 `viewSelection.rules`。第一项状态事实
是原生人物 `swimming`；普通 Mesh 缺少该事实时明确不可用。`resumeCameraViewSelection()`
恢复自动选择；未声明规则的文档保持旧相机行为。选择模块只返回视角意图，由同一个
CameraController 在固定步的输入/相机事务里提交。设计取舍见
[状态视角设计](superpowers/specs/2026-09-14-camera-view-selection.md)。

#### 先判断扩展属于哪一层

| 需求 | 应修改的位置 | 边界 |
| --- | --- | --- |
| 改距离、俯仰、FOV、跟随或过渡参数 | 项目 CameraDocument；可复用资产标定归 [preset-content/config/cameras](../packages/preset-content/config/cameras/README.md) | 不修改车辆物理 spec 或操控 profile；Playground 保存项目文件不等于发布共享预设 |
| 同一种算法增加游泳、探索等构图 | CameraDocument 的命名 `views`，复用已有 kind | `swimming` 可以是项目 viewId；通过 `viewSelection.rules` 显式绑定，复用已有拍摄算法 |
| 接入新人物、动物或载具 | 既有主体适配器、资产事实和必要预设；遵循[主体接入规范](asset-production-integration.md#新主体的镜头与输入接入) | 适配器提供实际身体、眼位、朝向等事实，不决定视角优先级或包含调参表 |
| 已有算法不能表达新的拍摄方式 | `packages/three-world/src/camera/strategies/` 与同包 `src/config/camera/` | 策略返回候选姿态和自身历史，由现有 controller 提交；不持有可写主相机或另设时钟 |
| 根据游泳、瞄准等状态自动选择视角 | `packages/three-world/src/camera/view-selection.ts` 集中选择；规则定义归 `src/config/camera/` | 与几何求解策略分开，只向现有 controller 提交选择意图；不在人物、地图、UI 和 Host 各写一套判断 |
| 展示和编辑参数或未来的选择规则 | Playground 现有 `src/camera/` 编辑器，Creator 的现有发现入口 | 消费 SDK 公共字段和真实可用能力；不复制默认表、解析器或执行逻辑 |

字段、单位、默认值及派生产物的维护步骤只在 [SDK 配置说明](../packages/three-world/src/config/README.md)
维护。公共 CameraDocument 类型和实际解析器决定可用字段，文档中的未来设计不构成
可用 schema。不同场景需要不同数值时，使用命名视角或显式覆盖，不加入场景名、
资产 ID 的隐藏算法分支。

#### 状态驱动视角的扩展合同

扩展状态或规则时，在同一份变更设计中明确以下合同并验证实际消费者。只为当前
用例增加必要的选择能力，不预建通用行为树、全局注册中心或新的相机包。

1. **状态事实与镜头选择分开。** 游泳、骑乘、瞄准等事实由拥有该状态的运行模块
   提供。选择逻辑消费已提交的事实及主体 generation，不根据动画名称、UI 选中项
   或重复的水深检测推断状态。项目规则关联实际状态与已声明 viewId，不接收任意
   脚本表达式。新增事实时先接通真实提供方，不能只增加一个未消费的配置字段。
2. **一个选择位置。** 在现有 World 固定步生命周期内集中求出当前选择，明确它与
   输入方向基准、物理后主体采样及相机提交的先后关系。重复观测、渲染或截图不能
   触发切换。选择不变时不反复调用切换入口，不重启过渡或覆盖玩家的环绕输入。
3. **控制权先于玩法优先级。** 保留 Episode 独占、作者镜头与受控跟随的显式交接。
   自动规则不得夺取作者镜头、编辑会话或录制控制权。Episode 的显式视角要求不能
   被玩法规则覆盖；若录制需要自动选择，必须在同一运行时合同中显式表达，由同一
   选择逻辑执行，不能在录制器另写规则。租约释放继续走既有恢复流程。
4. **重叠规则有确定结果。** 设计中列出自动规则的适用条件、优先关系及同优先级
   的稳定裁决方式，不能依赖监听器调用顺序。玩家显式选择默认保持到主动交回自动
   选择或生命周期使它失效；更具体的产品行为需显式声明。配置引用不存在的视角
   仍属于无效配置；合法自动规则因当前主体缺少锚点而暂不可用时，保留当前合法
   选择并反馈原因。无合法选择或显式请求无法执行时明确报告执行失败，不能偷偷
   套用人形预设；可选自动规则不可用本身不构成作品失败。
5. **退出时重新求值。** 入水时临时选择游泳视角；上岸时根据当前主体、仍有效的
   显式选择和其他规则重新决定视角，不无条件恢复入水前缓存的相机坐标。入水后
   上车、切换人物或修改文档时，旧主体的恢复记录必须失效。reset 回到已封存基线，
   清除临时选择；过渡、环绕意图和缩放的保留或重置由同一生命周期合同规定。
6. **调试能解释选择原因。** `inspectCamera().viewSelection` 说明当前采用哪条规则、状态来自哪个
   主体、为什么更高优先级请求生效、为什么候选不可用，以及是否正在过渡。编辑器
   展示同一结果；未观测和不支持不能伪装成已生效。反馈不成为额外生产门禁。

当前规则按数值优先级从高到低选择，同优先级按文档顺序。进入/退出延迟使用同一
固定时钟；选择不变时保持玩家环绕意图，不反复切换。游泳事实在一次物理步中改变，
下一固定步准备输入时生效。应用编辑草稿期间暂停自动选择；释放或重置后恢复。
Episode 默认锁定片段视角；只有显式 `start.cameraViewSelection:'automatic'` 才运行
同一个状态选择器。不存在另一套录制或 Playground 规则。其他状态按此合同逐项接入
真实事实，不根据动画名或视角名称猜测，也不要求每个生产项目添加状态规则。

#### 扩展如何验收

维护者按改动范围验证公共入口和实际消费者。参数改动核对解析、来源及实际效果；
新增主体或算法复用已有公共相机契约测试。状态选择实现需覆盖：入水/上岸、状态
短暂抖动、手动选择与自动规则冲突、过渡中再次切换、主体更换、reset，以及 Episode
接管和释放。抖动抑制若需要，应有明确的模拟时间语义，不使用独立墙钟计时器。

SDK、Playground、Creator 与 Episode 对同一规则和配置的消费必须一致；新增 schema
字段要有真实执行者、编辑/发现入口和有效性观测。测试跟随其所属模块，跨包流程才
做集成测试。不重复运行源码未变的完整回归，不将这些维护检查加入每次生产任务。
生产文档仅补实际可用接口、最小绑定方法和限制；不复制本节的开发设计流程。

## 画面与生产

`world.createPresentation()` 将纯世界输入、模型输出和 DOM UI 分开。模型返回
真实源帧身份后，HUD 才能对应历史状态；未知映射不能靠猜测固定延迟补齐。
重置使源帧身份失效。

Creator 先短测关键接缝与交互，修复后复查受影响部分，再用紧凑的完整真实输入计划
覆盖代表性路线、互动、核心功能及动作结果。录制长度由覆盖需要决定；内容容量与
实测录制时间分别说明。episode.json 的定时步骤按 durationSeconds 的真实时间执行输入，
按键保持到 keysUp。可选 driveTo 步骤按车辆实际状态计算输入，以 timeoutSeconds 限时，
到达后提前结束；复用 SDK 路点输入计算，仍由同一控制器和物理执行，不另建模拟时钟。
具体输入与结果见 Creator 编程指南。operations_get 返回操作与完整结果；
world_read_playtest 按录制时间范围读取位置、速度、骑乘、镜头和键盘采样，不重新
执行世界。采样身份属于原录制，不能直接证明当前源码状态或玩法合格。
提交使用同一 MCP session 中最新的完整合格录制，重新校验当前源码、运行时、episode、
证据文件和资产策略。调试后完成代表性真实录制再提交。交付包含自检录像、最终开场、
全可玩区俯视图、重要对象三视图和源码/运行时身份；技术合格不等于玩法或视觉验收。
详见 [Creator 交付契约](../packages/creator-host/README.md#verify-and-deliver)。
Episode 在独立生产副本中，用同一 SDK 记录六段 30 秒动作，之后制作十套风格。
录制中每帧来自真实模拟，动作事件来自执行证据。视频请求准备完成与最终视频完成
分别表达；执行范围见 [数据生产](three-sdk-data-production.md)。

## 验证

先检查接口消费者和场景条件，再验证真实输入、动作转换、失败结果、reset 和录制。
Creator 和 Episode 都要验证，某一侧通过不替代另一侧。运行时检查见
[专项检查表](reviews/runtime-deep-review-checklist.md)；纯文档检查链接、声明和
schema 主题提取。云任务、部署和外部审核依照实际任务授权执行。
