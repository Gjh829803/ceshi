# 可扩展运行时与内容接入设计

状态：已完成独立设计审查，并获用户授权分阶段实施；不表示 R1–R6 已实现。车辆按需诊断和固定翼自绘入口是本次独立的局部实现。本文不将它们算作运行时重构完成。

## 1. 结论与边界

2026-09-10 实施中用户进一步明确：内容在 Playground 调好后，由 Codex 按接入 Skill
完成整理、绑定与验证。长期目标是资产数量增长不要求重构核心加载和执行流程，同时允许
后续 NPC 自主行为及 Agent 叙事通过现有实体/命令/任务/事件边界扩展。
以下包构建、索引和检查工具作为可选辅助，不要求所有内容完全工程化注册。
需要稳定的是内容与运行实例的分离、共享依赖/释放、行为合同和真实消费闭环；
具体资源、binding、配置和代码接线可以由 AI 按 Skill 维护。

参考的业界职责划分是稳定 ID 与依赖加载（[Unreal Asset Manager](https://dev.epicgames.com/documentation/en-us/unreal-engine/asset-management-in-unreal-engine)）、
共享资源引用生命周期（[Unity Addressables](https://docs.unity.cn/Packages/com.unity.addressables%402.3/manual/MemoryManagement.html)）
以及跨帧行为任务（[Unreal Ability Tasks](https://dev.epicgames.com/documentation/unreal-engine/gameplay-ability-tasks-in-unreal-engine?lang=en-US)）。
在本 SDK 中落实这些原则，仍保留普通 Three 与已有 owner，不照搬完整引擎框架。

保留“普通 Three 创作 + SDK 稳定执行”。将“先在 Playground 调好，再人工教 Agent 接入”改为：**能力与资源具有同源定义，Playground 调试它，SDK 执行它，Creator 发现并绑定它，Episode 独立验证同一份定义和运行时。** Playground 是调试客户端，不是发布源，也不是与 SDK 平行的实现。

这需要两条主线同时规划、分阶段交付：

1. 可组合运行时：共享物理、按 actor 实例化、共享交互资源、持续动作任务、动画事件与姿态交接。
2. 内容接入工程：包内独立维护资源、动作绑定与操控配置，构建派生目录和工具入口，按身份保存验证与发布结果。

单纯增加资产 manifest 不能解决人物与 NPC 不可组合的问题；单纯拆运行时也不能解决资产持续入库时的重复登记和发布漂移。两者不能混成一个巨型注册中心。

不建设强制场景语言、通用 ECS、行为树编辑器、全套战斗系统或网络多人同步。本轮“多人协作”指多人开发内容；“多个角色”指同一世界的玩家/NPC。二者均不意味着联网多人游戏。GASP 动力身体、任意骨架自动重定向和百人同屏性能各自需要后续验证。

## 3. 方案取舍

| 方案 | 优点 | 长期问题 | 决策 |
| --- | --- | --- | --- |
| 保留现有单角色路径，只加目录和说明 | 改动小 | NPC/共享目标瓶颈保留，接入数量增加后持续侵入入口 | 不作为长期方案 |
| 新建统一 ECS/插件内核，把一切变成组件 | 理论上一致 | 大面积改写成熟控制器，创作受框架约束，验证规模失控 | 不采用 |
| 保留现有世界/命令/求解器，抽出必要 owner；内容包在构建阶段汇合 | 增量验证、职责清楚、普通 Three 不变 | 需要明确阶段边界和跨消费者契约 | 推荐 |

“共享”指共享时钟、物理服务、身份与事务，不要求 KCC、车辆刚体和飞行动力学使用同一种位移算法。“统一入口”指同一 execute/operations，不要求连续 WASD 每 tick 生成 operation。

## 4. 扩展单位与身份

六类定义分别处理，不能共用一个含糊的 `asset` 状态：

| 定义 | 提供什么 | 不自动提供什么 |
| --- | --- | --- |
| Model resource | 几何、材质、骨架、文件来源 | 动作、碰撞、控制器 |
| Animation resource | clip、轨道、源 rig、时长/采样信息 | 可执行玩法、目标占用 |
| Rig binding/profile | 骨骼映射、坐标/单位、参考姿态、必要身体标定 | 任意比例兼容或自动高质量重定向 |
| Motion profile | 控制器引用、默认参数、碰撞/机械/座位约定 | 模型或第二套物理世界 |
| Action definition/binding | 动作任务、资源声明、动画选择、阶段事件及结果 | 仅靠动作名称推断场景条件 |
| Integration package | 上述定义的版本依赖、示例、测试入口与发布组织 | 运行实例、全局状态或任意代码自动加载 |

运行时实体 ID、资源 ID、动作定义 ID、rig ID、控制配置 ID 和 operationId 分别稳定。重复 ID 是接入错误，名称相同不是可覆盖授权。角色 generation 区分 reset/despawn 前后实例；资源不可变内容 hash 区分同 ID 的版本内容；Three UUID 与 Rapier handle 只作当前实例内部索引。

显示名和搜索词可改，稳定 ID 不随翻译变化。代码 API 版本、资源内容版本、rig 兼容版本分别表达。第一阶段使用精确依赖与 lock，暂不引入复杂版本范围自动求解；发布后的旧项目按锁定闭包复现，不静默漂移到 latest。当前未发布 API 可同步迁移实际消费者，不为历史未发布接口建立永久兼容分支。

## 5. 内容包与构建产物

每个提交包拥有独立目录和 manifest；模型、动画、操控、动作可以分包，相互引用，避免每加一个动作复制人物 GLB。原始 DCC/FBX 工程保留在制作侧，运行时仅收实际使用资源。来源与许可遵循现有资源记录。

建议的 author manifest 只登记事实与引用：package ID/version、维护责任、定义路径、精确依赖、示例入口、测试入口。行为条件与参数不在 manifest 再手抄一份，引用 SDK 实际定义。manifest 不执行脚本；构建扩展是仓库审查过的工具代码。

构建解析依赖后产出三个视图：

- 运行时定义及资源闭包：保留现有资产加载和哈希校验协议；只打包项目选择的资源与必要依赖。
- Agent 索引：用途、可绑定对象、参数、约束、schema/示例入口。生成自资源和能力定义，不从目录 README 猜能力。
- 开发接入报告：注册与重复 ID、缺失依赖、rig/clip 引用、示例打包、实际工具可达性、内容与源码身份。

`assets/three-creator/catalog/<asset-id>.json` 是资产条目的唯一来源，export/import 脚本更新所属源文件。`asset-catalog.json` 由这些文件确定性生成，供 Host 消费，不直接编辑，也不作为旧条目的回退来源。SDK、Host、示例和测试同步使用当前契约，不保留旧目录读取、覆盖合并或双协议解析。删除资源前检查反向依赖，不能让发布包依赖开发机器上碰巧存在的文件。

示例 topic、源码目录与胶囊打包清单由一个构建清单派生，消除新增示例要改三个位置的问题。包只需登记示例一次。生成物排序稳定，构建/CI 只比对漂移，不在 CI 自动写回仓库。发布任务消费同一份已验证依赖闭包。

**权限与接入分离。** 新包被发现不等于加入生产白名单。开发 Playground 可以加载显式选中的本地待验证包；Creator 继续按冻结策略过滤。测试报告分别列出 registered、policy-allowed、compiled、behavior-verified、visual-reviewed、released，不合成一个含糊的 ready。每项记录证据身份；过期验证为 stale/unknown，不冒充失败或当前成功。

### C1 的最小同源定义与迁移方式

不从 TypeScript 函数体或 README 自动推断动作能力。现有 `SkillId`、`SKILL_DEFINITIONS`、`CHARACTER_CAPABILITIES`、ActionSystem 条件、Source101 clip roles 与 Host 提示需逐项收敛：

- **动画变体作者**修改动画资源条目和 `actionId + rigProfileId → clip roles/events` 的 binding。无需改 input/operation 或 MCP 分派。
- **行为作者**修改所属 SDK action module。模块导出可序列化 descriptor：稳定 ID、参数 schema、资源需求、已命名条件/原因码、完成语义、binding slots；任务实现使用同一模块的条件判定。数值来自现有 tuning，描述不手抄另一份阈值。
- **运行时**调用真实 predicates 决定 eligibility，返回被拒绝的条件 ID/原因和当次实测值；descriptor 仅说明条件，不充当模拟结果。尚不能数据化的条件保留运行时函数与明确源码入口，不构建通用规则 DSL。
- **受信构建器**只加载仓库中经过审查的 SDK 模块，序列化其 descriptor。package manifest 仅引用已导出的定义，不携带可执行表达式、任意 import URL 或 shell 脚本。项目自带源码仍只读取声明/源身份，或查询实际浏览器实例，不在 Host 上求值。

C1 首批接通一个 `pickup` 和一种动画 binding；检查 descriptor 原因码与真实拒绝路径是否一致，再推广到其他行为。目录生成工具验证稳定 ID、引用和依赖；行为测试验证结果。不能用“存在 descriptor”替代运行时支持。

旧元数据迁移到新的实际定义后，移除被替代的副本；过渡期用一致性检查明确唯一权威，不能双向同步两个可编辑源。导出的 Agent 索引是构建产物，编辑它不会改变行为，也不接受为修复 runtime bug 的入口。

## 6. Playground → SDK → Agent 的具体路径

1. 开发人员创建或更新所属包，Playground 直接加载该包的 runtime definitions 和本地内容。
2. 调整参数先进入实例 override；界面区分当前生效值、未保存值和原始默认值。
3. 导出带来源 profile ID/hash 的参数 patch；写回包的规范配置由明确保存操作完成。禁止“Playground 调好了”却只改 UI localStorage 或复制另一份默认表。
4. 开发检查验证受影响输入、绑定和消费者；确定性构建生成索引、catalog 和包锁。
5. Creator 从实际发布包发现配置，按需求自绘/选择模型、绑定条件与锚点，使用既有工具查询结果。
6. Episode 锁定同一源码、资源、参数与输入合同，独立录制。发布记录包含包锁、runtime hash、工具版本和证据索引。

每种操控配置明确三种参数：可自由调节的控制参数、影响几何/物理须联动的结构参数、尚不可实例化修改的固定标定。结构参数变化时，由同一 resolved spec 生成实际碰撞与供作者使用的机械约定。Visual root 任意缩放不能隐式替代结构配置。飞机当前固定标定应如实暴露；后续若允许不同翼展/质量，必须将求解器从全局常量迁移到实例 resolved airframe，并验证碰撞、惯量、升力与轮组一致。

已有汽车、摩托、飞机作为首批迁移样本，不要求先把所有载具包装成同名工厂。达到相同接入质量的标准是能被发现、读懂、绑定和验证，而不是 API 名字对称。

## 7. 动作资产的大规模扩展

动作数量增加时，新增 clip 应主要改内容包与 binding；新增行为才改执行逻辑。分三条接入路径：

- 同行为新增动画变体：引用既有 action ID，提供 rig 兼容、clip、循环/混合、动作事件标定。沿用已存在的条件/锁/完成判定。
- 新的纯表现动作：声明 animation-only，接入同一动画 owner 和可取消的播放结果；不改变碰撞、持有或导航，不宣称 gameplay 能力。
- 新的持续行为：实现受控任务，声明动态资源、进入/退出、取消与中断、目标条件和终态；再绑定动画。保持 world.execute 与 operations 唯一外部执行协议。

动作定义负责“为什么可以做、做完是什么”，动画 binding 负责“用哪套骨架、哪段动画表达”。同一 pickup 可绑定不同形象的抓取动作；同一 clip 也不能在不同角色上共享 mixer 或可变骨骼。

事件由固定步动作实例产生，携带 operationId、actor generation、loopIndex、eventId 和源时间。跨越时间区间只提交一次，大步长按事件序处理；重复截图、定位预览和次要混合 clip 不产生 gameplay 事件。grip/release 在世界唯一安全提交点重新检查目标并原子更新归属、附着和碰撞。坐下或拾取 operation 成功后，座位占用/持有关系仍存续，不能随着任务结束释放。

持续任务最初只提供少量明确阶段，不建立通用脚本解释器。资源粒度先为移动、全身动画、姿态、左右手、物品与目标槽位；动态 actorId/targetId 经 schema 校验后解析资源集合并按稳定顺序原子获取。失败默认拒绝并给出原因，不隐式永远等待。取消请求、取消获准和清理完成分别处理，终态不能先于真实状态。

Rig 检查分结构与效果：骨骼映射/轨道目标/单位/hash 可自动检查；肩膀扭曲、脚滑、抓点偏离需要绑定样例和视觉验收。换比例、骨架或物理身体不能复用旧验证身份。后续根运动、IK、动力身体都从姿态/身体交接边界接入，不复制实验场的世界和主循环。

## 8. 世界和 Actor 的责任

世界拥有一个 Rapier world、唯一固定步进、导航服务、实体/目标表、资源预约及 operation 状态。Actor 拥有自己的控制器、输入意图、动作状态、mixer、骨架、持有关系引用和 generation。当前输入目标、镜头目标和 Actor 身份分开。

固定步顺序：输入边沿/命令 → 资源仲裁 → 导航与动作意图 → 物理目标 → 唯一 owner 的物理推进阶段 → 接触与动作结果 → 固定姿态/状态快照。

“唯一推进”不等于每 tick 只调用一次 Rapier.step：当前车辆在 60 Hz SDK tick 内以 120 Hz 子步积分。保留子步数、子步前求力和子步后回读；角色增多不得各自重复整个世界的子步。验收统计外层推进 owner 与受控子步预算，不通过删除子步来满足字面上的“一步”。渲染只插值已提交状态。加载的墙钟超时与任务的模拟时间超时分开；暂停不消耗动作时限或槽位预约时长。

共享目标采用现有实体身份与 MapInteraction 扩展，不建立同名孤立的物理目标。导航到达、胶囊可站立、动作接触可达分别判断。预约 token 在 grip/sit 提交时转为持有/持续占用；目标移动/移除、角色移除、取消和 reset 均走明确清理。删除一个 NPC 不 dispose 共享世界。

保留现有 ThreeWorld、execute、OperationLedger、导航与 WriteClaim。新增长任务与动态资源仲裁，不把当前纯 plan 命令数组解释成跨时间顺序执行。对外能力查询区分 definition-present、resources-loaded、actor-bound、eligible；实时 eligibility 引用实际 owner 的条件检查，避免另写一份“看起来可用”的判断。

### 共享资源与实例释放

沿用并扩展 [assets.ts](../../../packages/three-world/src/assets.ts) 的加载缓存与资源清理，避免新建第二个资产加载器。包/世界资源服务持有按内容 hash 键控的只读 bytes、源 clip、原始几何与材质/贴图；Actor 通过 lease 引用它们，持有自己的骨架、mixer、控制器和可变材质副本。改变单角色材质不得污染共享模板。

加载请求携带实体 generation 与取消信号。部分加载失败释放已取得 lease；despawn/reset 后异步完成只释放资源，不重新注册旧 actor。最后一个有效引用消失时才能 dispose 共享 GPU 资源，取消一个请求不取消其他角色已共享的成功加载。世界 dispose 关闭实例并清理该世界的引用；进程级缓存如保留须有容量/回收策略，不把所有历史包永久驻留内存。

验收覆盖两个相同模型实例、一个变体、一个中途失败加载、反复创建/删除与世界释放，分别核对 mixer/listener/body 和共享资源引用。离线资源 hash 去重与运行时可变实例隔离是两件事。

## 9. AI-facing 使用合同

AI friendly 不是所有实现都塞进提示词，也不是增加一个万能 buildScene。采用分层发现：

1. 发现时只返回稳定 ID、用途、已支持范围和简短限制；按任务相关性与分页控制体积。
2. 选择后返回 resolved 默认配置、最小绑定合同、必要资源依赖与完整可读示例。包依赖由构建解析，Agent 不手填传递依赖列表。
3. 实例绑定后，从同一个 eligibility owner 查询当前可执行性。区分未加载、未绑定、缺场景条件、被占用和不支持。
4. 连续控制走同一语义输入；离散动作走既有 execute/operations。调用者无需指定骨骼、动画文件或内部任务阶段。
5. 操作后返回真实终态与对象关系。失败提供主体/目标/条件和相关查询入口，不自动传送角色、缩小碰撞或改写场景。

以“NPC 拿杯子”为例：选兼容人形与 pickup 能力 → 为杯子绑定真实物体/握点/接近位置 → 请求指定 actor 的 pickup → 在同一 operation 查询导航、对齐、抓取和终态。动画 clip 的选择属于已安装的 binding。若只有动画没有行为，发现结果只承诺播放；若杯子没有碰撞/目标，报告缺失条件，不从名称猜它能被拿起。

以“自绘飞机”为例：发现固定翼 profile → 读取尺寸/轮组/座位合同 → 自绘并绑定 → 查询输入与当前状态 → 使用真实输入起飞。无需阅读空气动力学源文件；超出固定标定范围时可返回结构参数不可覆盖的明确说明，由维护者扩展求解器。

工具协议不为每个资产或动作增加一个 MCP 方法。既有 search/describe/schema/examples/execute/inspect 继续工作，新 ID 进入同源索引；复杂动作的详细阶段只在查询该 operation 时展开。默认响应预算用实际案例和 token/工具调用测量控制，不以删掉必要前置条件换取短文本。

开发者路径与生成 Agent 路径分开：开发者运行 package 检查、调试、视觉评审和发布；Agent 消费已发布或显式选择的项目 SDK，不被要求每次创作重复跑包入库检查。项目可修改自己的 SDK，但 Host 不执行项目源码来生成能力索引；只能读取其声明/源身份或查询真正运行起来的实例。

AI-friendly 验收不只看 schema 成功：同一任务让 Agent 新建一辆车/飞机、选择一个动物主体、替换一个既有动作变体、操作共享目标；记录首次完成率、缺省配置可用性、错误恢复步骤和源码阅读次数。效果与任务复杂度分组，不能用简单车型成功推断全部动作包都容易使用。

## 10. 观察、批量检查与协作

观察按 actor/vehicle/target/operation 查询，默认摘要，详细轮胎、骨架、任务和占用信息显式请求。来源包含 world revision/generation、模拟 tick/time、resolved profile 与 runtime/package 身份。未知、失效与测量失败各自表达；短时打滑或动作过渡不自动判成故障。

多人协作按实际 owner 拆 PR：资源制作与来源、rig/动作绑定、运动求解器、世界交互、Host/发布。负责人由团队填写，不在模板预设虚构姓名。共享接口先确定再并行，每个包独立文件；代码所有权审查集中到被修改的运行时 owner。资源 PR 可以独立验收，新增行为 PR 必须携带最小真实消费者。

批量检查选择 package ID 或 git diff，扩展到反向依赖与实际消费者；未受影响的包复用同身份结果。一包失败返回其具体原因，继续完成其他包的报告；整体命令是否非零取决于检查结果。检查不自动授权外部生产、修改白名单或发布。CI 使用 mocked cloud transport。

验证结果复用键明确为：`hash(选中包的传递依赖内容闭包 + 相关 resolved 配置 + 实际 runtime 身份 + 工具/检查实现版本 + 检查输入与环境规格)`。记录检查类型和判定版本。资源级检查只需其资源/检查器身份；行为和视觉检查必须包含运行时与场景/输入。若当前运行时是单体 bundle，行为证据必须使用完整 runtime hash，不伪装成已实现模块级精确依赖分析。

无关资产包入库不改变已有包的依赖闭包；修改求解器、rig、参数、样例或测试实现则使相关证据失效。人工视觉评审引用确切媒体 hash 与内容身份；审批截图 A 不批准重新生成的截图 B。发布必须同时展示当前包锁与评审匹配结果，不能只看最近一次绿色报告。

每次升级比较两个成本：开发接入触点数/漏接率，以及生成 Agent 首次成功率/返工次数/工具调用/耗时。性能记录单角色与 3/10 角色固定步 p50/p95、渲染耗时、mixer/body/collider 数和生命周期资源回收。没有旧多人运行时就不伪造多人前后对比。单角色 p95 回退超过任务书的 10% 阈值需同场景复测并解释。

## 11. 分阶段交付与拒收条件

| 阶段 | 实际交付 | 必须证明 | 不可替代的证据 |
| --- | --- | --- | --- |
| L0 局部闭环 | 按需车辆诊断、固定翼自绘入口 | 读取不改变状态；真实输入可驾驶/起飞；默认输出不增肥 | Creator 和 Episode 使用当前构建；不是仅返回配置 |
| R0 基线/决策 | 当前能力、owner 表、合同、单角色性能与录制基线 | 旧任务书差异已核对，未验证项明确 | 本文只完成源码审查与设计部分，性能/全行为基线另补 |
| C1 内容接入基础 | 包源定义、确定性 catalog/index/示例派生、开发批量检查 | 首批模型/动作/操控各一包可通过实际工具消费；重复 ID、缺资源、过期证据有测试 | 修改一个动作资源不需再手改多处发现/发布入口 |
| R1 共享模拟服务 | 完整人形与普通物体借用同一物理服务 | 唯一推进 owner，保留原有子步预算；现有 KCC/车辆行为不变 | 接触与生命周期浏览器回归 |
| R2 多 Actor 与导航 | 玩家 + 2 完整 NPC、独立输入/mixer/控制 | NPC 真实导航与碰撞，玩家可骑乘，移除不伤其他实例 | 3/10 角色首次性能测量与本地 Episode |
| R3 共享目标 | 原子预约与持续占用/持有 | 两 NPC 同 tick 争用恰一成功；取消/reset 无孤儿资源 | 场景实体、物理本体、归属三者一致 |
| R4 动作任务/事件 | pickup/sit 首批迁移，安全取消与一次性事件 | grip 不重放，任务终态与实际结果一致 | 不同渲染率/暂停/跨事件步长及目标失效 |
| R5 姿态/绑定边界 | 源姿态、物理目标、overlay、显示分离 | 显示扰动不污染源姿态；根位移不重复 | 动作与骑乘视觉复核；不等同 GASP 移植 |
| C2 动作包扩展 | 新变体接入、依赖与 rig 检查、同源能力发现 | 添加动画变体走内容路径；新行为走任务路径 | 自动检查和视觉证据分别报告 |
| R6/C3 发布闭环 | Creator/Playground/Episode、包锁与证据、可回退发布 | 相同合同与 runtime hash，能追踪已发布和仅合并版本 | 最终真实输入/视频/性能复测与人工动作验收 |

C1 可以在 R0 决策后先做，不等待全部多角色重构；C2 的持续行为扩展依赖 R4/R5。R6 随每阶段同步迁移，不留到最后才发现 Host 无法操作新 actor。不要把 R1–R6 压成一个大 PR。

每个阶段必须是可运行纵向切片，拒收只有接口/空目录、调用层测试替代真实动作、为过测试关闭碰撞、变更未发布契约却保留两套永久执行协议。

## 12. 下一步可执行顺序

1. 收尾 L0 的独立审查、相关门禁、构建身份与飞机视觉检查。局部变更不承诺解决多角色或批量动作。
2. 完成 R0 未运行基线，给出角色/目标/operation/动画事件的明确合同决策；将本文评审意见落实为设计修订。
3. C1 先迁移 Source101 模型、现有交互动作和 road/plane 配置：在同一个包构建结果上跑 Playground 与 Agent 示例，并删除这几个样本被替代的重复登记。
4. R1–R4 按共享物理 → 多角色 → 共享目标 → 持续动作推进，每步保留现有驾驶、相机与录制。
5. R5/C2 接住大量动作和后续姿态模块，最后按 R6/C3 做发布、性能和视觉总验收。

设计评审重点是 owner、扩展单位与阶段顺序，不是先批准一大批 API 名称。首批实现验证收益后再推广到剩余历史资产；没有真实消费者的扩展点不提前实现。
