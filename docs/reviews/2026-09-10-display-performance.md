# 显示功能性能排查

## 结论

显示提交引入了可避免的后台目录扫描，以及未开启锚点时的辅助位置采样。已在本地取消这些工作。当前正常材质下的明显持续卡顿，尚不能归因于这两项：同环境移除后台扫描、诊断 renderer 和渲染钩子后，采样帧数没有改善。CPU profile 的主要可定位热点是既有 `VehicleCameraQueries.sync()` 及其几何版本检查、世界矩阵/包围盒更新。

## 范围与证据

- 用户当前页面为 `http://127.0.0.1:5186/`，服务来自 `.worktrees/render-preview`，仍是显示功能预览版本。该页面没有启用诊断预览，普通材质、全场景、辅助关闭；界面曾读到 8 次渲染回调/秒。
- 主干测试服务 `http://127.0.0.1:5187/` 包含已经推送的 `7d1414db` 及本次本地修复；与 5186 的运行字节不同。
- 在独立 Chromium 页面中注入计时，通过 CDP CPU Profiler 做同场景、同尺寸的顺序对照。未修改用户页面的相机、位置或模拟状态。测试页面额外承担 profiler/无头浏览器开销，下面的帧数用于相对比较，不代表用户设备最终帧率。
- 5186：约 6.4 秒采样中，目录刷新 22 次、合计 42.1 ms，单次最大 4.4 ms；关闭目录刷新后，两个样本均为 22 帧。
- 5187：完整显示路径与临时移除显示目录刷新、诊断 renderer/渲染钩子的两个样本均为 20 帧，采样约 6.4 秒。诊断 canvas 都未启用。
- 5187 CPU profile 总时段约 7.87 秒，`VehicleCameraQueries.sync()` 两处调用栈包含子调用共约 2.23 秒，约占 28.3%。这是下一步应追踪的 CPU 热点，不是本次显示改动带来的代码：该文件最后修改提交为 `4d5c120a`，早于显示功能的 `9358e478`。
- 本地 CPU profile 文件保存在 `.worktrees/render-preview/.codex-tmp/display-perf-current.cpuprofile`、`display-perf-no-metadata.cpuprofile`、`display-perf-no-display.cpuprofile`；`current` 为最后一次 5187 样本。注入脚本同目录 `display-perf.ts`，不进入产品代码。

## 本次修复

1. `main.ts` 中默认画面且显示检查关闭时，`refreshDisplayMetadata()` 立即返回，不再重建对象目录、双次扫描物理世界、序列化行数据、计算所有载具座位位置。打开面板、显式修改设置、切换地图仍强制刷新，保证首次打开和生命周期更新正确。
2. 诊断渲染的 overlay 数据读取仅在交互锚点实际启用时调用 `readDisplayTargets()`。白模、深度、碰撞辅助等无关模式不再逐帧查询全部座位的世界位置。
3. `display-smoke.ts` 注入只存在于测试页的计数器，验证默认运行不重建目录、纯画面模式不额外采样锚点。修复前分别稳定失败：目录读取从 6 次增长到 9 次；画面切换额外触发锚点采样。

## 仍然存在的成本与边界

为保持源截图与模型输入干净，诊断模式当前使用第二个 WebGL renderer：正常游戏为一次场景渲染；诊断画面通常两次；画面叠加线框最多三次。该开销仅在预览实际生效时存在，首次进入新模式还有 shader 编译和 GPU 资源分配成本。本次没有更改源渲染与采集契约。

本次不宣称整体卡顿已经解决，也不以跳过相机碰撞、降低物理频率或冻结载具换取帧率。相机查询热点需要按固定步与呈现调用拆分、检查静止载具重复刷新成本，并保留玻璃、开口、动态轮组、碰撞安全性与镜头遮挡契约。
