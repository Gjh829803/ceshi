# 产品与系统边界

> 本文描述产品目标和长期边界。当前交付状态以[项目总览](00-project-overview.md)和[当前实验记录](10-current-experiments.md)为准。

## 1. 产品目标

用户输入一句话、图片或其他视觉参考，Coding Agent 使用本 SDK 创建一个可玩的 3D 白膜世界。玩家直接操作这个确定性的白膜世界，实时世界模型把它渲染成风格完整、细节丰富的最终画面。

系统链路：

```text
用户文本/图片
    ↓
Coding Agent
    ↓ 编写 TypeScript 世界代码
Three.js 白膜游戏运行时
    ↓ 白膜 + 深度 + 法线 + ID + 动作 + 语义
实时世界模型
    ↓
最终游戏画面
```

后续还会加入独立的运行时操作链路：

```text
用户运行时需求
    ↓
Director LLM
    ↓ 结构化观察、命令、任务和回执
World Control Gateway
    ↓ 通过权限与一致性校验后在固定 tick 提交
Three.js 白膜游戏运行时
```

Coding Agent 负责创作和修改世界代码；Director LLM 负责在已运行世界允许的能力范围内进行即时编排。两者都不能绕过白膜运行时直接改变最终画面的逻辑真相。当前只有第一条链路的室外 Alpha 已运行；Director 和实时世界模型仍处于方案/接入准备阶段。

## 2. 世界真相

白膜游戏运行时是以下内容的唯一真实来源：

- 主体和客体的位置、旋转、速度与生命周期
- 碰撞和刚体结果
- 地形和可通行空间
- 玩家当前控制的主体
- NPC 位置、路径和行为状态
- 动作名称和动作阶段
- 游戏规则、胜负、计时与触发事件
- 摄像机位置、朝向和参数

世界模型只改变最终视觉表现，不得决定上述逻辑。

## 3. 白膜建模边界

判断某个元素是否需要出现在白膜中的规则：

> 如果它影响移动、碰撞、导航、遮挡、镜头、关键轮廓或游戏规则，它必须存在于白膜世界；如果它只影响材质、氛围、装饰和表面细节，则交给生成式渲染层。

例如：

| 元素 | 是否需要白膜 | 原因 |
|---|---:|---|
| 可攀爬高塔 | 是 | 影响轮廓、碰撞和导航 |
| 完全不可交互的远处窗户 | 否 | 仅为表面细节 |
| 玩家会绕开的桌子 | 是，简单盒子即可 | 影响移动和遮挡 |
| 墙面的裂纹和苔藓 | 否 | 交给渲染层 |
| 可以驾驶的汽车 | 是 | 是可控主体和物理实体 |
| 天空中的非交互云层 | 通常不需要几何 | 可由环境语义和渲染层生成 |

## 4. 主体、客体与控制权

主体和客体不应设计成两种互斥的实体类型。两者都属于 `Entity`：

- 主体是当前由玩家、NPC 或脚本控制的 Entity。
- 客体是当前未被主动控制，主要被观察、碰撞或作用的 Entity。
- 控制权可以在 Entity 之间转移。

例如玩家进入汽车后：

```text
人形失去玩家控制权 → 汽车获得玩家控制权 → 镜头切换到车辆预设
```

玩家离开汽车后执行相反过程。

## 5. 系统不负责的内容

第一阶段不追求：

- 传统 PBR 材质和高质量离线渲染
- 大量精细家具和装饰模型
- 复杂角色捏脸和服装系统
- 完整商业游戏编辑器
- Agent 每帧参与玩家控制
- LLM 绕过命令协议直接修改 Three.js、Rapier 或导航内部状态
- 让世界模型决定物理、碰撞或胜负
- 任意插件和任意底层 Three.js 代码作为默认创作方式

## 6. 产品成功标准

系统成功不以白膜画面精美为标准，而以以下能力衡量：

- Coding Agent 能稳定生成可启动、可操控的世界。
- 玩家输入具有稳定、可复用的运动手感。
- 白膜状态与最终生成画面的空间关系一致。
- 主体跨帧保持身份、位置和动作连续性。
- 世界模型出现延迟或失败时，白膜模拟仍然正确运行。
- SDK 错误能够被 Coding Agent 理解并自动修复。
- 后续 Runtime Director 的每次世界修改都能被授权、验证、回执和确定性重放。

其中前六项是第一期和 World Model 接入需要逐步验证的目标；最后一项是 Runtime Director 实现后的验收目标，不能用于暗示该模块目前已经存在。
